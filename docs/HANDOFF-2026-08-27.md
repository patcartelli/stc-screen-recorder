## STC-259 — read this first, it is the live one

Five sightings. Three proposed mechanisms refuted by measurement. The fifth
sighting (run 33101235431) finally discriminated, because the instrumentation
added earlier that day did its job:

```
[writer-gate] harness started (pid 4368)
Error: writer-gate: harness did not finish within 45000 ms; killed its process group.
```

`harness started` printed, the **encoder inventory line did not**. So the
compile is exonerated and `VTCopyVideoEncoderList` blocked and never returned.

**The unifying explanation: any first touch of the paravirtualized H.264
encoder can block indefinitely on some runners.** CI reports its hardware
encoder as `paravirtualized:Apple Video Encoder`, a passthrough to a host
shared with other tenants. Before today the first touch was `AVAssetWriter`'s
lazy compressor creation — exactly where both original STC-254 crash reports
pointed. Now it is the inventory query. Same cause, moved.

That accounts for every observation: intermittent (host contention), unrelated
to what is tested (a docs-only PR still writes an MP4), `WriterGate` blameless
across ~1000 clean local iterations, never reproducible on real hardware.

### The next step, concretely

1. Bound the encoder query: run `VTCopyVideoEncoderList` on a queue with a
   timeout and treat no-answer as an `environmentFailure` — the same shape the
   harness already uses for the filename collision. It must stay
   distinguishable from a `WriterGate` regression, which is the trap that cost
   an afternoon earlier today.
2. Then consider the same for the harness's first `AVAssetWriter` append.
3. Only then ask whether `helper/src/CameraCapture.swift` and `Capture.swift`
   need it. A real recording wedging on a contended encoder would be a product
   bug — but nothing has shown that on real hardware, and it should not be
   assumed.

Full history is in the STC-259 ticket, including the three refuted mechanisms
so nobody re-runs them.

### Increment 3's hardware results, measured not assumed

- Camera PTS is genuinely session-relative — the upper bound against
  `anchors.stop.t` holds, so no rebase.
- **Two concurrent H.264 encodes cost the display track nothing measurable:**
  862 frames, 0 dropped, 0 non-monotonic at 3840×2160 alongside a 720p camera.
  Recorded in `PHASE-2.md` with its caveats.
- **Camera open is far slower than the spec assumed.** A cold Elgato Facecam
  4K on USB2 took **2.246 s merely to open**; warm, its first frame landed at
  604 ms. Phase 0's ~1035 ms warm-up figure understates the cold case and
  overstates the warm one. This is why the camera is opened off the critical
  path, and why the grant test's lower bounds had to be loosened after they
  nearly tripped.

### A sequencing constraint that is load-bearing

A take with `camera.present: true` **cannot be opened until 4b lands** —
`session.ts` demuxes the camera track now (4a), but nothing draws it, and
increment 5's UI toggle must not ship before 4b or the app will offer people a
recording it cannot display. The grant test *produces* such takes on a granted
machine.

## Traps added to CLAUDE.md today

Each cost real time:

- an `AVAssetWriter` append and its teardown must not overlap (STC-254)
- a fault does not pick one signal — the same use-after-free arrived as SIGTRAP
  on CI and SIGSEGV locally
- the macOS Camera pane lists only apps that have already *requested* access,
  so a bundle that merely reads `authorizationStatus` can never be granted
- Camera TCC inherits through the bundle, same as Screen Recording (verified)
- `gh pr checks --watch` exits 0 when no checks exist yet — success by finding
  nothing to do, in a place where success reads as verification

### One more worth adding, not yet written down

**A new bound must be checked against every bound already covering the same
code, not just against the thing it bounds.** Three bounds added to
`writer-gate` in one day each failed to fire: a synchronous call blocked the
event loop its timer lived on; collected stderr was discarded because the
promise never settled; and an inner bound was set exactly equal to the outer
one so the informative message always lost the race. Each was individually
sound and lost a race nobody checked.

## How today actually went, for calibration

Every plan written today contained defects that only surfaced when someone
traced the actual execution — not when the tests passed, and not on re-reading
the plan. The recurring shape was writing the correct principle in prose and
violating it in the code beneath: "open the camera off the critical path" above
an inline blocking call; "exact integer nanoseconds" above a `Double`
round-trip; "this is the most important assertion" above bounds that could not
catch the likely failure.

Ten defects were found after implementation in increment 3 alone — six in
review, three from one run against real hardware, one self-caught. Four were
in the plan itself.

The practical lesson for whoever picks this up: **the review loop and the
hardware run are not ceremony.** They are where the defects were actually
found, and skipping either would have shipped them.
