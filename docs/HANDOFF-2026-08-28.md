## STC-259 — root-caused. Read this before touching the gate.

**The 26-minute "gate stall" was TEARDOWN, and it was never the encoder.**

Three of us had theorised about it, including me, twice. The answer was in the
log of run 33108160534 the whole time and nobody had read it:

```
19:26:01  > node scripts/gate.mjs
19:27:07  FAIL: TimeoutError: decoder flush did not complete within 60000ms
19:53:35  ##[error]The operation was canceled.
```

The gate did **not** hang. It failed correctly 66 seconds in, a bound fired and
named the culprit, and then the process sat 26 more minutes in `finally` on an
unbounded `browser.close()` — closing a browser whose renderer is wedged never
returns. A job timeout reports as *cancelled*, so it read as an unexplained
hang and the real error scrolled past unnoticed.

That half is fixed. #30's `closeQuietly` bounds teardown at 30 s. Same failure
now takes 96 s and says both parts out loud.

**I was wrong twice and both mattered.** I told the user the cause was likely
`VideoEncoder.configure()` blocking synchronously — the encoder is not involved
at all. And I believed the fix we shipped was bounding the gate body when it
was actually bounding teardown: right fix, wrong reason. Read the failing
step's log before theorising.

### The remaining fault, in two modes

CI's macOS runners are VMs sharing video hardware with other tenants, and it
intermittently stops answering. Two distinct shapes, both confirmed:

| | fires | means |
|---|---|---|
| **Mode A** | `decoder flush` inner bound, 66 s | page alive, a JS timer could run |
| **Mode B** | outer bound, 185 s | renderer **wedged**, no in-page timer can run |

Mode B is direct evidence for the blocked-main-thread hypothesis, and it means
**no in-page instrumentation can ever diagnose it**. Only out-of-process
evidence can — Chrome's own GPU logs would be the next avenue if anyone wants
to chase it.

`decode.ts` now reports, on the failure path only, how far the decoder got:
chunks submitted, frames emitted, `decodeQueueSize`, state, and what
`isConfigSupported` says for hardware and software. That discriminates "never
started" from "stalled at the last frame" — different bugs. It helps Mode A
only, by construction.

### What #39 changed, and why it is not "hiding the failure"

`npm run gate` now retries up to 3 times and keys **strictly** on the
`ENVIRONMENT:` label the gate prints when a bound fired. Any `FAIL:` line, a
death by signal, or the runner's own bound disqualifies a run from retry. After
3 environment failures it emits an Actions `::warning` saying *"DID NOT RUN …
This is NOT a pass"* and exits 0.

The reasoning, because it will look like weakening a correctness gate: a red X
that means either "you broke determinism" or "Apple's shared GPU didn't answer"
is **ambiguous, not loud**. Now red always means the code and SKIP means the
machine. Every skip still records the full diagnostic, so evidence accumulates
without master being red half the time.

`STC_GATE_FAULT=environment|regression` and `STC_GATE_ATTEMPT_LOG` make both
paths reachable and counted; each guard was mutation-tested (dropping the
`FAIL:` disqualifier, the signal check, or the retry condition each breaks 3
tests). `npm run gate:once` is the raw single-shot gate.

**Watch the skip rate.** If gates start skipping most runs, the guarantee has
quietly stopped being checked even though nothing looks wrong — the same
"succeeds by finding nothing to do" trap in a new place.

## The E2E flake — diagnosed, partly fixed, not proven

Two separate things were found under this heading.

**A real defect, measured and fixed (#32).** Six suites each ran
`app/build.mjs` per launch: 17 builds in one `vitest run app/test`, 5 in flight
at once, all writing `app/dist/{main.mjs,preload.cjs,renderer.js}`. esbuild
truncates before rewriting, so a sampler caught all three at **zero bytes**
mid-run — `renderer.js` 282 times. An Electron launch landing in that window
loads an empty renderer and `#takes` stays empty, which is exactly the reported
symptom. Built once in `vitest.global-setup.ts` now; `app/test/build-once.test.ts`
stops it coming back — and it caught the #28 collision on its first day.

**Saturation, addressed but unproven (#34).** A full run peaked at FIVE Electron
apps at once; the `e2e` project now serialises to ONE, at a measured cost of
+17 s. **This is not proven to reduce the flake** — both arms were green on an
idle machine, and the load experiments that would have proven it were
invalidated (see below).

## Measurement mistakes I made, so you don't repeat them

Four separate measurements in this session were wrong, all in the same family:

1. **Leaked CPU spinners.** A load experiment's `(while :; do :; done) &`
   subshells survived `kill $(jobs -p)` and a `pkill` whose pattern did not
   match the resulting bare `/bin/zsh`. They ran 26 minutes at 8 cores, load hit
   **404**, and every before/after number taken in that window was worthless —
   including one that appeared to show a fix making things worse. Kill by PID
   and confirm with `ps`.
2. **Self-matching greps.** A process counter spawned `grep`, and `ps` listed
   the greps, which matched each other's patterns — a phantom baseline of 2 with
   nothing running and a "peak 6" that was mostly artifact. List `ps` once and
   filter in-process with `startsWith` on the absolute path. Calibrate against a
   known state (0 idle, 1 with one app) before believing anything.
3. **An uncommitted change carried into the control arm.** `git checkout <sha>`
   brought my edited `vitest.config.ts` along, so both arms had the change and
   produced identical numbers. Commit first; verify the tree at each arm.
4. **A `git checkout master` that silently failed** — master is checked out in
   the main worktree, so both arms ran the same branch. Use a detached SHA from
   a worktree.

Also: `execFileSync` returns **stdout only**. An assertion on a stderr message
fails for the wrong reason. Use `spawnSync`.

## The merge script

Its exit code has now been wrong in **both** directions and is fixed in #36.
It exited 0 after giving up (that was an invocation piping through `tail` — the
script was right), and it exited 1 after a merge that **landed**, because
`gh pr merge --delete-branch` deletes the *local* branch, which means switching
off it, which fails from a worktree. It now merges, re-reads the PR's state as
the authority, and deletes the remote ref over the API. A failed cleanup is
reported and does not change the exit code.
