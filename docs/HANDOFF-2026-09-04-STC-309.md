## What STC-309 is, in one paragraph

The helper now samples which macOS pointer is showing (`NSCursor.currentSystem`,
30 Hz, on its own thread), classifies it against the four `NSCursor` built-ins
measured at recording start, and writes `{t, kind: "cursor", shape}` into
`events.json` **version 2**, only when the shape changes. The transform
(STC-239, already merged) draws the matching artwork. Verified by a human
watching an export of a real take: I-beam over a text field, hand over links,
arrow elsewhere, click highlight under the I-beam, in step with the video.

## What closed, and what the evidence actually is

**The spike (increment 0).** `NSCursor.currentSystem` sees other apps' pointers
from the background helper. 599 samples in 20 s, 0 nil, on a plain `Thread`
with its own `CFRunLoop`, so no main-thread requirement. The I-beam over a text
field matched `NSCursor.iBeam` byte-for-byte; a second run over a link emitted
`pointingHand`. All four shapes match their built-ins on the user's machine.
The private-API fallback (`CGDisplayCopyCursorForDisplay` via dlsym) was never
needed and is not in the code.

**The spike is a helper command, not a throwaway.** `cursor-probe` runs the
production `CursorSampler` in the production process shape and reports the
references, every signature change, what would have been emitted, and the
per-sample cost. `tools/test-host --cursor-probe` drives it under the bundle's
TCC identity. Re-run it when a machine or macOS version changes.

**One measurement overruled the ticket's plan.** The ticket put the sampler on
the tap's run loop so one thread would own event ordering. A sample costs
**1.04 ms mean, 41 ms max**, which is not a cost the tap can carry (a starved
tap is disabled by the system). The sampler has its own thread; `orderedEvents`
restores time order when the file is written. That is #75.

**References are measured at start, not baked in.** The ticket wanted a table
from the spike. A table drifts the first time the pointer-size accessibility
setting or the display scale changes, and both change the bytes. Measuring
`NSCursor.arrow/.iBeam/.crosshair/.pointingHand` in the same process at the same
settings makes those cancel.

**The watch (increment 4's gate).** An 11 s take recorded from the app: 726
moves, 6 clicks, 37 shape changes. The user exported it with
`scripts/export-one.mjs` and confirmed all three things the gate asks for.
Sidecars are pinned as `fixtures/real-session-cursor/` with
`helper/test/real-events-cursor.test.ts` on top. That test pins the PRODUCER'S
CONTRACT (v2, change-only, ordered across both clocks, names the compositor can
draw, interleaved with motion); it cannot tell a right shape from a uniformly
wrong one. Only the watch does.

## Two bugs found that were on nobody's list

**`stop()`'s own tap disable came back as a re-enable, and was acted on.**
CoreGraphics reports `tapEnable(false)` back to the tap callback as a
`tapDisabledByUserInput` event. The helper counted it as a re-enable AND
re-enabled the tap it had just disabled. Invisible for the life of the project
because nothing asserted `tapReenables == 0` until STC-309 did and got 1, on a
build where the sampler was already off the tap's thread. Fixed in #76:
`decideCursorEvent` names the reason (`timeout` vs `userInput`),
`stoppingBegan` is set BEFORE the disable, disables after it are counted apart
(`stats().tapDisabled.afterStop`) and not acted on. A `timeout` in that
breakdown would be real starvation.

**A swiftc warning on the events literal.** `["version": 2, ...]` needed an
explicit `as [String: Any]`. Cosmetic, fixed in #75.

## What I got wrong today, so you don't repeat it

1. **I wrote three Swift files on a Linux box with no compiler.** One line
   failed on CI: `let rl = CFRunLoopGetCurrent()` is `CFRunLoop?`, not
   `CFRunLoop`. Annotate the type. Everything else compiled first time, but the
   honest statement is that CI was the first compile and the PR said so.

2. **The first grant-test failure had two stories and I nearly picked one.**
   `tapReenables: 1` could be the sampler starving the tap or the helper's own
   stop. I added a control (`STC_NO_CURSOR_SAMPLER=1`, a take that differs only
   by having no sampler) and the reason breakdown BEFORE deciding. Both builds
   showed the same count; the sampler was never involved. The repo's rule
   ("compare against a control that differs ONLY by the thing under test") is
   what settled it, not reasoning.

3. **"No cursor at all in the video" was the raw capture.** The user opened
   `display.mp4` from the take folder, which never has a cursor by design
   (`showsCursor` is off; the pointer exists only in an export). I checked the
   transform for a regression before asking which file was watched. Ask first.
   `node scripts/export-one.mjs <take> 30` is the fastest watchable file.

4. **The lossy test's 223 vs 463 frames looked like stdout throttling
   capture.** It was two VFR runs seeing different screen activity right after
   a camera take. Re-run alone: 276 vs 264. A VFR frame count on a live screen
   is not a stable number; do not read a regression into one run of it.

5. **I force-reset the remote branch after each merge**, and the user's local
   copy still had the old tip, so their push of the fixture commit was
   rejected. `git pull --rebase` fixed it. If a human shares your branch, tell
   them before you reset it.

## The one thing that connects nearly all of it

Every wrong number today was a measurement that could not see what it was
being read as evidence about: a re-enable count with no reason attached, a
frame count on a moving screen, a video file that never carries a cursor.
Each was resolved by adding the missing discriminator (a reason field, a
control run, the question "which file?"), never by arguing harder about the
number. The repo's CLAUDE.md already says this several ways; today added
three more entries.
