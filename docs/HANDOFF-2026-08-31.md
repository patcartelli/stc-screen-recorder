## What I got wrong today, so you don't repeat it

**I published a 100% skip rate that was 60%, and retracted a claim built on it.**
`gate-skip-rate.mjs` searched the whole-job log for `Determinism gate DID NOT
RUN`, which `transform/test/gate-retry.test.ts` prints verbatim into the **Test**
step. Every run that ran the unit tests read as a skipped gate — including runs
where the gate passed in nine seconds. The boundary claim (last pass `cb03ee9`,
first skip `9df1e27`) came from the same method and is **retracted**.

**I got the step-attribution direction exactly backwards.** I wrote that
attribution "ages out within a day or two" and advised measuring fresh runs.
Measured over 12 runs: nothing younger than ~200 min has it; everything between
212 and 319 min does. It *appears* hours later. A just-finished run is the one
you cannot measure.

**I put `test:slow` into CI without reading the warning in the file I was
enrolling.** `ring-overflow.slow.test.ts` says in its own header that it "timed
out on CI at 180 s", which is why it lived outside CI. It passed three runs and
failed the fourth, reddening an unrelated PR.

**I asserted in a code comment that software decoding could not change a pixel.**
It changes the pre-encode hash (`10a05a33` → `bc03e397`). H.264 decode is
bit-exact in YUV; the RGBA that reaches the canvas after colour conversion is
not. Measured false and corrected before merge.

**I nearly recorded the clamshell control as a second closed-lid run.**
`ioreg -r -k AppleClamshellState -d 4` prints a subtree, and grepping it for the
first `Yes`/`No` token matches something unrelated — it said `Yes` while the
property-scoped read said `No`. Had I not re-checked, I would have written "the
camera sometimes works in clamshell" and undermined the root cause I had just
established.

**Three separate guards I wrote were beaten by prose rather than code** — a
`SEEK_MS` check tripping on its own comment, a `parseProject` check satisfied by
a comment mentioning the function, and a marker check that flagged its own file.
The comment stripper now lives once in `transform/test/_source-text.ts`.

## The one thing that connects nearly all of it

**Every wrong answer above came from a measurement reading something *wider*
than intended.** Whole-job logs instead of one step. Raw source instead of code.
Other checkouts instead of this one (`vitest.slow.config.ts` was unscoped and
globbed `.claude/worktrees/`, which made a mutation test report "2 failed | 2
passed" where the passes were other agents' trees). Two rasterizers instead of
one. An `ioreg` subtree instead of one property.

Each produced a confident, plausible, wrong number. Three were published before
being caught. **When a number surprises you, check what it was measuring before
you believe it.**

The near relative: a decision recorded in a comment, overridden without reading
it. That is the `test:slow` mistake, and the information was one line above the
code being moved.

## Hardware notes for the next session

- **The grant that matters belongs to the terminal**, not to `STCTestHost`. The
  grant tests spawn the helper directly, so it inherits the launching process's
  TCC identity. A fully granted bundle says nothing about whether they can run.
- Cameras enumerated here: `FaceTime HD Camera`, `Elgato Virtual Camera`
  (`'virt'`, idles ~1 fps), `Patrick's iPhone Camera` (Continuity). The Elgato
  Facecam 4K is not present. `pickCamera` ranks correctly among these.
- Clamshell needs the HP Z27 plus AC power, both present. Read the lid with
  `ioreg -r -k AppleClamshellState -d 4 | grep '"AppleClamshellState"'` — scoped
  to the property, or it is not about the lid.
- `tools/test-host` batch mode is the best way to capture a take non-interactively
  and get the helper's full event transcript:
  ```
  open -W tools/test-host/STCTestHost.app --args \
    --helper "$PWD/helper/build/stc-helper" --dir <sessionDir> --ms 12000 --camera \
    --out /tmp/result.json
  ```
- A leftover `electron .` holds the display and shows up as E2E flake. Check
  `ps -Ao pid,command | grep '[s]tc-screen-recorder'` before debugging one. A
  loaded machine is the commoner cause: the suite failed 4 tests at load 62
  (Lightroom, WindowServer) and passed at load 27, unchanged.
