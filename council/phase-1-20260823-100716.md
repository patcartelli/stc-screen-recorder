## Reviewer A

## Issues

1. **This is not a single-sprint MVP for one developer.** The stated phase includes deterministic rendering, a long-running native capture daemon, four media tracks, cross-process supervision, TCC/signing investigation, segmented recording, live stats, display reconfiguration, device-loss handling, WebCodecs composition/export, and a 30-minute fault-injection soak. Any one of helper reliability, timeline alignment, or Electron/WebCodecs export can consume the sprint. The soak harness is not a finishing task; it will expose defects requiring another implementation cycle.

2. **The “vertical slice” has no defined synchronization model for real media.** The document establishes clock facts, but not the rule that turns screen PTS, camera PTS, mic PTS, system-audio PTS, CGEvent timestamps, segment boundaries, and display-reconfiguration gaps into one project timeline. `render(project, events, t)` can be pure only if `project` contains an immutable, normalized timeline/asset manifest. Without that, alignment will be re-derived opportunistically in preview and export, violating the stated non-negotiable.

   The architectural rule should be: **capture writes timestamped immutable assets; ingest produces one canonical project timeline; rendering resolves every source frame and event only through that timeline.** Capture must not be the place where preview/export alignment logic lives.

3. **Segmenting output without a segment manifest breaks the promised timeline.** “Segment output every N minutes” is not enough. Each segment needs stable track identity, start/end PTS, discontinuity markers, codec parameters, dimensions, audio sample rate/channel layout, and a rule for overlap/gap at rollover. Otherwise a segment boundary, encoder restart, or SCStream rebuild will create an undefined gap or duplicate interval during export.

4. **Display hot-swap behavior is not specified at the user-visible level.** “Rebuild the SCStream against the new config” leaves the central questions unanswered: which display is recorded after a display is removed; whether a resolution/scale/color-space change creates a new track segment; what frame is displayed during rebuild; and whether export holds the prior frame, fades, letterboxes, or marks a gap. Under the stated goal—“while the world changes”—this is a correctness defect, not merely hardening.

5. **The current scope treats camera, mic, system audio, display changes, and device loss as simultaneously required despite calling camera/mic off the critical path.** That is contradictory prioritization. If camera and mic are off the critical path, Phase 1 should not spend its critical path implementing their disconnect behavior, alignment, and export mixing. System audio is also a separate reliability and permission surface even when obtained from `SCStream`; it should not be bundled into the first proof of deterministic visual capture/export.

6. **Increment 0’s test gates are underspecified and likely unachievable as written.** A canvas preview and a WebCodecs export cannot generally be compared by “frame hash” unless both hash the exact same pre-encode RGBA buffer, with defined pixel format, color conversion, alpha treatment, dimensions, font loading, and device pixel ratio. Hashing decoded MP4 output will fail due to lossy encoding. “Two independent exports … byte-identical” is not a useful first gate unless the encoder configuration, metadata, timestamps, muxer behavior, and hardware/software backend are controlled; many valid encodes differ bytewise.

7. **The pure transform boundary is right, but the boundary as written is incomplete.** `render(project, events, t) → FrameState` appears to cover cursor and animation state, but not deterministic media-frame selection, decoded-frame availability, color conversion, or asset reads. If `FrameState` includes source-frame references, their resolution must be deterministic and timestamp-based. If it includes pixels, the renderer needs an explicit asset resolver. Otherwise decoder scheduling will leak back into the sinks despite the stated rule.

8. **The helper protocol is too weakly defined for process supervision.** JSON lines plus separate “reliable” and lossy channels does not define request IDs, acknowledgement semantics, state transitions, helper restart recovery, session ownership, partial-file finalization, or what Electron does if the helper crashes during recording. A `stop` request issued while capture is reconfiguring or segment rollover is occurring has no stated outcome. This will be discovered during the first real recording.

9. **The first milestone cannot be completed in one sitting.** Increment 0 contains schema design, fixture production, deterministic animation semantics, canvas rendering, WebCodecs encoding/muxing, image comparison infrastructure, and deterministic-export investigation. It is a substantial subproject, not a one-sitting milestone. The first milestone should be a hand-authored fixture rendered to a canvas at two arbitrary seek times, with a checked-in pixel snapshot; export comes after that.

## Missing

- **A canonical session/project manifest.** Define the persisted object that maps every raw asset and event into project time: track IDs, time origins, PTS ranges, segment order, gaps/discontinuities, display configuration changes, track availability, and alignment offsets. `events.json` and `anchors.json` alone are insufficient.

- **A minimum shippable Phase 1 definition.** “One CFR MP4 with cursor overlay and camera PiP” is not a scope boundary when the preceding increments include all audio tracks and resilience behavior. Specify the required inputs and the explicit exclusions:
  - required: one selected display, cursor events, one fixed-duration recording, one export;
  - optional/later: camera PiP, microphone, system audio, segmentation, display hot-swap, device loss, live stats, and the 30-minute all-fault soak.

- **A fixed-display recording rule.** Specify whether Phase 1 records a display ID, a window, or the currently selected physical display; what happens if it disappears; and whether Phase 1 simply stops with a recoverable error. “Stop cleanly and preserve the completed portion” is a valid MVP behavior.

- **An alignment acceptance criterion.** “Camera↔mic measured at +1.8 ms median” is evidence, not a product requirement. State the allowed screen/camera/cursor/audio offset, how it is measured over a recording, and whether drift correction is supported. Without this, “align” cannot be declared done.

- **The export fidelity contract.** Define output dimensions, frame rate, pixel format, SDR color space, audio codec/mix policy, and whether a source frame is held across gaps. This is necessary to make `greatest PTS ≤ t` operational across all tracks.

- **A testable reconfiguration/disconnect policy.** For each source, define whether the project timeline records a gap, a held frame, black/silence, a removal of the PiP, or a terminated recording. Then define a fixture-based export test for that event. Do not implement watcher infrastructure before this behavior exists.

- **A realistic roadmap ordered by value.** The highest-value next phases are:
  1. **Reliable session ingest and recovery:** manifest, segment finalization, crash recovery, source-gap representation, and alignment diagnostics. This compounds if deferred because every editing and export feature will otherwise encode assumptions about raw files.
  2. **Review and trim UI:** playback, scrubbing, trim handles, cursor/camera placement, and visual presets. This uses the author’s interaction and visual strengths and turns capture infrastructure into a usable product.
  3. **Deterministic export parity:** project fixtures, seek/export parity tests, export queue/progress/cancellation, and failure reporting.
  4. **Additional capture sources and resilience:** camera, mic, system audio, hot-swap, and long-duration recovery only after the one-source project model is stable.
  5. **Multi-take/project management and distribution:** only after one session can be recovered, reviewed, edited, and exported reliably.

- **The opportunities enabled by the architecture.** If the canonical project timeline is actually implemented, the pure transform unlocks deterministic seeking, reproducible exports, thumbnail generation, headless regression renders, editable visual presets/templates, later multi-take composition, and rendering the same project at multiple output formats without recapturing. Those are reasons to protect the boundary now; they are not reasons to build all capture modes now.

## Overconfidence

- **“The helper inherits Electron’s TCC identity” is stated too strongly.** A child process relationship alone is not a sufficient identity model for TCC. Bundle placement, code requirement, signing chain, helper embedding, entitlement requirements, and the specific protected service matter. The proposed experiments are correct, but until they pass on the actual bundle layout, this belongs in “to verify,” not “settled architecture.”

- **The self-signed certificate plan is presented as a reliable stable-TCC solution before it has been verified.** The document acknowledges the experiment but still says it “gives a stable identity so TCC grants survive rebuilds.” That is the conclusion under test. State the fallback if it fails: use a locally installed development identity/Xcode-managed signing, or accept a deliberate permission-reset dev workflow until distribution signing exists.

- **“System audio … same stream, separate output type” understates integration cost.** Obtaining audio samples from ScreenCaptureKit does not settle permission behavior, timestamp mapping, sample format conversion, discontinuities during stream rebuild, muxing, mix policy with microphone audio, or export synchronization.

- **“Camera/mic are already off the critical path” is unsupported by the stated MVP output.** The required output explicitly includes a camera PiP, and the capture increment includes mic and system audio. They are on the critical path as written.

- **The phase-0 performance findings do not establish composed-path viability.** Capture encode throughput does not prove that Electron can decode 4K source video, composite canvas/WebGL layers, render text/cursor animation, and encode CFR output at the required rate. The first performance experiment should measure the complete chosen export path at target duration and resolution, not isolated capture throughput.

- **“Preview frame hash = export frame hash” assumes identical rendering environments.** Canvas preview and export can differ through scaling, color management, font rasterization, GPU backend, and pre/post-encode representation even with a shared transform. What can be guaranteed is identical `FrameState` and, if deliberately architected, identical pre-encode raster input.

- **The 30-minute induced-fault soak is presented as a Phase 1 gate without a recovery budget.** A first soak will likely identify leaks, deadlocks, finalization failures, and timestamp discontinuities. Passing it is a separate stabilization phase, not a task to append after the feature work.

## Verdict

**Revise it.** The architecture’s core rule—one deterministic project-time transform shared by preview and export—is the right foundation and unlocks editing, reproducible rendering, regression fixtures, and future output formats, but the proposed Phase 1 attempts to validate every capture and resilience axis before proving one usable path. Cut Phase 1 to: a fixed selected display, cursor overlay, fixed short recording, explicit session manifest, deterministic seekable preview, and one SDR CFR export; allow a clean stop-with-warning on display loss, omit camera/mic/system audio, omit segmentation and live stats, and replace the full fault-injection soak with one ordinary 5–10 minute recording/export. Build recovery/manifest correctness next, then review/trim UI and visual composition, then export reliability, then additional sources and long-run resilience; deferring the manifest/discontinuity model is the risk that compounds most because every later feature will otherwise invent incompatible timeline rules. **Instruction: rewrite Phase 1 around one canonical session manifest and one fixed-display/cursor/export path, moving all extra tracks and change-resilience behavior into explicitly sequenced later phases.**

## Reviewer B

## Issues
Phase 1 is not a single-sprint MVP for a solo developer. Six increments (0–5), a blocking signing setup that is not an increment, four mid-recording risk classes treated as first-class, and a correctness gate that requires deterministic WebCodecs+mux, cannot be finished in one sitting — and increment 4 is the first time the stated goal (`record → align → composite → export`) actually happens. Under a 1–2 week solo sprint the leftover work is not “polish”; it is the slice.

The increment-0 gate “two independent exports of the fixture are byte-identical” will stall the sprint. WebCodecs + any JS MP4 muxer routinely writes non-stable atoms (creation time, `mvhd`/`tkhd` timescales, encoder SEI, box ordering). Frame-hash equality of the composited bitmap is the real contract; byte-identical containers is a different, likely false, claim. The first afternoon spent hex-diffing `mdat` is time not spent on `render()`.

There is no decode / seek / segment-stitch layer in the architecture diagram or the increments, but increment 4 cannot exist without one. `render` is pure and must not touch decoders; something else must, given `t`, open `display.mp4` / `camera.mp4` (VFR, possibly many segments), pick `greatest PTS ≤ t`, and hold. That layer is where VFR-vs-CFR phase error, segment boundary PTS resets, and Electron memory pressure live. It will be invented inside increment 4 and force a rewrite of both the session layout and the transform inputs.

“Stats are non-blocking and lossy” and “control messages use a separate reliable channel” disagree with the only channel drawn: JSON lines over stdin/stdout. One pipe cannot be both drop-oldest and reliable. Mid-build this becomes a second fd, a unix socket, or a priority field that does not actually prevent a stats flood from delaying `stop`. The helper-control-plane increment is already in progress without this decided.

Work order contradicts the stated architectural rule. The non-negotiable is `render(project, events, t) → FrameState` as the single transform; increment 1 (helper control plane) is already underway and increment 0 (schemas + fixture + transform) is not. The helper will emit whatever the tap happens to produce; `events.json` / `anchors.json` will be reverse-engineered from that, and the purity rule will be patched around capture artifacts instead of constraining them.

`stateAt(n)` is specified as seek-equivalent to stepping at 120 Hz, with no cost model. A 5 s fixture hides this. A 30 min soak at 120 Hz is 216 000 ticks; if increment 4/5 implement seek by replaying from tick 0 per exported frame, a 60 fps export is ~2.3×10¹⁰ step operations. Without checkpoints or a foldable log, increment 5 is the moment the transform is rewritten.

TCC “one grant, inherits Electron’s identity” is treated as settled. Screen Recording, Camera, Microphone, and Input Monitoring are separate TCC services and are often granted per-executable, not per-parent. The helper that actually calls ScreenCaptureKit / `CGEventTap` / AVFoundation is the binary that will be checked. Increment 2/3 can look finished on a machine that already clicked Allow during the spike and then fail on a clean launch or after a rebuild.

## Missing
A time box. “Sprint” is never defined, increment 1’s remaining work is “in progress” with no done-line, and signing is a prerequisite that sits outside the increment list. Without those, “is this one sprint?” is unanswerable from the text — the answer from the work listed is no.

The cut. The document admits “fully hardening all four is more than one increment” and then keeps all four tracks (screen, camera, mic, system audio), segmented writing, display hot-swap, device-loss, soak, and a live Electron shell in phase 1. It never names the minimum composed path. That decision is the whole question.

Protocol and session contract: message types, who may drop what, how `stop` is acknowledged, what a crash mid-segment leaves on disk, whether PTS is continuous across the N-minute cuts (N also unset), and how Electron reloads a session after a helper death. These will be discovered the first time start/stop is hit twice.

Audio’s place in `render`. `FrameState` is implied video-shaped; four audio clocks (camera, mic, sysaudio, plus whatever SCStream emits) have no mix function, no sink, and no alignment rule beyond “PTS used as-is.” Increment 4’s “one CFR MP4 with cursor overlay and camera PiP” either silently drops audio or grows a second pipeline that is not behind the transform.

`project` schema. The purity rule makes `project` the only place visual craft can land (PiP geometry, cursor scale, crop, zoom). It is unnamed. If increment 0 hard-codes overlay layout to get hashes to match, every later visual change forks the transform — the exact failure the architecture exists to prevent.

Entitlements, helper bundle layout, and the two signing experiments as a gated increment, not a sidebar. This machine has zero identities. Increment 2 cannot be honestly tested until (a) or (b) has been run.

Anything after phase 1. Non-goals are listed; phases are not. The document therefore cannot answer its own roadmap question. Highest-value next phases this architecture actually unlocks, in order, once a thin slice exists: (1) `project`-driven visual pass — zoom-to-cursor, PiP, cursor treatment — because `render` is already a function of `project` and this is the author’s leverage; (2) a timeline that only seeks `t` and re-calls `render` (cuts, holds, speed) with no recapture; (3) multi-take / session browser as a directory of already-valid session dirs. Uploads, HDR, cross-platform do not get cheaper by waiting, but they also do not compound. What does compound if deferred past a thin phase 1: signing/TCC identity, segment+PTS contract, helper crash semantics, and `stateAt(n)` cost. Those four become load-bearing the moment a recording longer than the fixture exists; changing them later invalidates every session on disk.

## Overconfidence
“Inherits Electron’s TCC identity — one grant” is an assumption. Phase 0 verified capture under some already-granted state; it did not verify a clean-boot, helper-only, four-service grant story.

`SCStreamConfiguration.capturesAudio` “avoids a second device path” is an API reading, not a soak result. System-audio under display reconfiguration (the exact combo increment 5 wants) is one of the known SCStream failure clusters. Treating it as settled in the same table as “we will observe thermal fade” mixes a hope with a measurement.

`displayTimeNs = displayTime × 125/3` is a fact about this Mac’s mach tick, stated as a product rule. The next machine, or a VM, will disagree. The settled rule should be “read the timebase; never assume 1 ns or 41.667 ns.”

Byte-identical export, 30 min soak of all four risks, and “the slice builds each in as a first-class concern” are presented as phase-1 scope. The honest-scope sentence already knows this is false.

“Ugly is fine” is used to wave away product surface, but increment 0’s gate is the opposite of ugly-is-fine — it is a determinism lab. That is the right instinct for the transform; it is not a reason to also take capture hardening, supervision, and soak in the same sprint.

Helper-as-child “means” TCC inheritance and a stable identity. It means a child process. Signing, entitlements, and which binary Apple attributes the tap to are separate facts, and this machine cannot currently sign.

## Verdict
Revise it. As written this is a multi-sprint systems program (Swift supervision + four capture graphs + Electron decode/seek + deterministic encode + soak), not a one-sprint vertical slice, and the first milestone a solo developer can actually finish in one sitting is increment 0 without the byte-identical clause — not “record → align → composite → export” with camera, mic, sysaudio, hot-swap, and a 30 min harness. Cut phase 1 to: schemas + 5 s hand-authored fixture + `render(project, events, t)` + canvas sink + WebCodecs sink gated on per-frame bitmap hash only; finish the helper control plane; port **screen + event tap only**, one file (no N-minute segments), no camera/mic/sysaudio, no display-rebuild, no device-loss path, no soak; Electron start/stop that produces one CFR MP4 with cursor overlay from that single screen track. That is the composed proof; everything else in the table is phase 2 hardening. Highest-leverage change: write `events.json`, `anchors.json`, and `project` (even if `project` is three fields) before another line of helper protocol, and make increment 1 consume those schemas rather than define them.

## Reviewer C

## Issues

1. **The plan is two sprints wearing one sprint's clothes, and the doc says so itself.** "Fully hardening all four is more than one increment" appears directly above a plan that builds all four *and* a soak harness that exercises them together. At this author's pace: increment 0 is 5–9 days (the gate debugging is the wildcard), increment 1 has 2–3 days left, increment 2 is 4–6 (segmentation and stats plumbing are new, not ported), increment 3 is 2–3, increment 4 is 4–7 (see Missing #1), increment 5 is 2–4 plus whatever the soak finds. That is 19–32 working days before soak remediation, which has zero budget because the soak is the final increment. What breaks: the sprint ends mid–increment 4, or the soak gets silently skipped — the one increment that covers the #1 risk.

2. **The increment-0 gate is unimplementable as written, and increment 0 is the foundation.** "Preview frame hash = export frame hash" admits three readings: (a) hash the decoded H.264 output — impossible, the codec is lossy; (b) hash the on-screen preview canvas against the offscreen export raster — fails, because a Retina preview canvas rasterizes at devicePixelRatio with the display's color profile while the export surface rasterizes at 3840×2160 sRGB, so identical draw calls produce different pixels; (c) hash the RGBA buffer handed to the encoder — achievable only if the preview is a *scaled blit of the export-resolution raster*, not an independent rasterization. Increment 0 will naturally build (b) and burn days discovering (c). State the rule: one rasterizer at export resolution; the visible preview is a downsampled copy; the hash is taken pre-encode. Likewise "byte-identical exports" will break on container metadata (mvhd/tkhd creation timestamps) depending on the muxer — specify hashing the elementary streams, not the file.

3. **Display-change semantics are undefined in the transform, but the schema is written before the helper runs.** A hot-swap rebuild produces a display.mp4 whose resolution changes mid-timeline. `FrameState` has no specified behavior for this (letterbox? crop? rescale cursor coordinates?), and the hand-authored 5-second fixture will not contain a display-change event — so the events/anchors schema gets built without the display-geometry timeline, and increment 2 or 5 discovers the omission, forcing rework of increment 0's artifacts. Either specify it now or cut hot-swap from phase 1 (recommended; see Verdict).

4. **The hold rule, applied to a disconnected camera, renders a frozen PiP for the rest of the export.** "Greatest PTS ≤ t; hold, never interpolate" is correct for VFR/CFR phase mismatch and wrong for track death: after `AVCaptureDeviceWasDisconnected`, the greatest camera PTS ≤ t is the last frame before unplug, held forever. The transform needs a track-liveness concept (track ended → omit PiP), and events.json needs a device-lost event. Neither is in the schema increment. Condition: any mid-recording unplug — which increment 5 deliberately induces.

5. **Dev-loop TCC grants attach to the wrong binary.** Running via unpackaged Electron attributes Screen Recording, Camera, and Accessibility grants to the Electron binary's identity, not the product bundle's self-signed identity. The signing section's experiments (a) and (b) will measure a different app than the one that ships unless they run against a packaged, self-signed app shell. What breaks: preflight passes in dev and fails in the packaged build (or the reverse), and the stable-identity claim gets "verified" against the wrong identity.

6. **The stats back-pressure rule states a policy, not a mechanism.** "Drop-oldest on full buffer, never back-pressure the capture graph" only holds if stdout writes happen on a dedicated writer thread draining a bounded queue, with no writes from any capture callback. A single blocking `print` in the capture path — or an Electron renderer stalled on GC long enough to fill the pipe — wedges capture, which is precisely the failure the protocol claims to exclude. One sentence in the doc fixes it.

## Missing

1. **The frame-provider contract — the largest gap in the document.** `render()` is pure and decoder-agnostic, so something outside it must turn display.mp4 + `t` into pixels. Export consumes `t` monotonically (sequential decode); preview scrubs (random access with GOP-boundary seek cost); both must resolve "greatest PTS ≤ t" identically, across segment boundaries, treating segments as one logical stream. "Sinks may not fork the transform" has an unstated sibling: **sinks share one frame provider.** Without a specified interface (decoder lifecycle, seek budget, cache window, segment stitching), each sink grows its own and they diverge in exactly the way the doc's own table row warns about. This is also why increment 4 is not "wiring" — it contains this subsystem, and it is described in one sentence.

2. **Export audio.** mic.wav and sysaudio.wav are captured; the deliverable says "cursor overlay and camera PiP" and never mentions audio. Which tracks, mixed how, encoded with what (AAC via WebCodecs AudioEncoder is version- and platform-dependent in Chromium), at what sample rate, with what drift correction between two independent clock domains over 30 minutes? Nothing. Decide now, because the answer constrains the anchors schema in increment 0.

3. **The muxer and the Electron pin.** WebCodecs emits encoded chunks, not MP4. 30 min of 4K60 at plausible bitrates is multiple GB; an in-memory mux OOMs the renderer. Decide: streaming/fragmented MP4 to disk via Node (e.g., mp4-muxer with a streaming target), and pin the Electron version — WebCodecs H.264 hardware decode *and* encode paths in Chromium are version-dependent.

4. **WebCodecs throughput evidence.** Phase 0's encode numbers are VideoToolbox-from-Swift. Nothing measures Chromium's WebCodecs decode+encode at 3840×2160 sustained, and increment 0's 5-second low-fidelity fixture cannot reveal it. Extend the fixture to 30–60 s at real 4K60 with an fps floor in the gate, or increment 4 commits to an unproven path.

5. **The coordinate-space rule.** CGEvent delivers global points (top-left origin, unscaled); ScreenCaptureKit delivers pixels (2× on Retina); the camera is its own space; hot-swap makes the mapping time-varying. State the rule: **convert at the boundary** — the helper emits cursor positions already in the captured frame's pixel space, so the transform only ever sees one coordinate space. A cursor drawn at 2× offset is the canonical bug here, and the hash gate will not catch it if the fixture's coordinates were hand-authored in the wrong space.

6. **Schema versioning and conformance.** events.json/anchors.json get a `version` field now — recordings outlive the code that wrote them, and this is cheap exactly once. Increment 2 needs a conformance test that real helper output validates against the increment-0 schema (the fixture is hand-authored; the helper will emit things it didn't model — flagsChanged, scroll, multi-display coordinates). After increment 2, re-author the fixture from a real captured session. Also state the ns→tick quantization (`floor(t_ns × 120 / 10⁹)` in integer math — 10⁹/120 is not an integer, so the rounding rule must be in the schema, not in each sink).

7. **Soak pass criteria, crash policy, and the live-preview non-goal.** "Exercise all four together" has no numeric threshold — phase 0 already showed thermal fade of 18.7 → 12.1 fps, so define the acceptance number (dropped-frame budget, encoder fps floor at thermal steady-state) or the soak produces vibes. State the helper-crash policy (phase 1: stop-and-save; segments on disk stay valid) and the orphan policy (helper dies with parent). State explicitly that there is no live preview during recording — it is a third sink with real-time decode of a growing file, and it will creep in mid-sprint if not excluded by name.

## Overconfidence

- **"Settled by phase 0 — do not relitigate" overreaches on drift.** The timestamp *conversions* are settled. The drift claims (`0.0000 ms`, camera↔mic +1.8 ms median) were measured in a 12-second one-shot. Clock-domain drift on USB audio and cameras is precisely the phenomenon that appears at 100× duration; the soak is 150× the spike's window. Treating a short-window median as physics means anchors.json gets designed as a one-time offset — make it a time series of anchor pairs, or phase-2 audio sync cannot be retrofitted onto phase-1 recordings.
- **"Export via WebCodecs" assumes the spike's numbers transfer.** They were VideoToolbox-from-Swift. Chromium's H.264 encode can silently fall back to software with no error — the WebCodecs analogue of the "prefer-hardware only" rule (detect and refuse software fallback at export start) is unstated.
- **Byte-identical exports are assumed, not shown.** Hardware-encoder determinism for identical input on one machine is likely; container-metadata determinism from a JS muxer is not. The gate as written may be unpassable for reasons having nothing to do with the transform.
- **"Camera/mic are already off the critical path"** is true capture-side only. PiP puts camera decode, a second frame-selection timeline, and track liveness onto the export critical path in increment 4 — the phrase hides the work.
- **Increment 4 is described as "wire real capture output through render()"** — one sentence covering VFR H.264 decode, the frame provider, CFR resampling, compositing, encode, and mux. It is the largest increment in the document and the one most likely to be standing when the sprint ends.

## Verdict

Revise. The architecture is right — the pure transform with two sinks and a small, signed helper boundary is the correct solo-maintainable shape, and phase 0's measurement discipline is real — but the increment list is roughly double a sprint, the foundation increment's gate is ambiguous in a way that will consume days, and the frame-provider, audio, and muxer decisions are missing exactly where they will force rework. The answer to the question is no: as written this does not fit one sprint. Cut phase 1 to the spine — transform contract (with the frame-provider interface written into it), screen + events capture with segmentation and stats, minimal shell, export = screen + cursor + mic audio, detect-and-clean-stop on display change, and a manual 30-minute soak with numeric pass criteria. Defer to phase 2: hot-swap rebuild and its transform semantics, PiP and device-loss behavior, system-audio mixing, and the scripted failure-injection harness (which should live alongside the hardening it tests). Beyond that, the highest-value phase is post-production on the pure core — cursor smoothing, click-zoom, keystroke overlay, reframed crops — because it is pure TypeScript with zero new macOS surface, it is the author's actual leverage, and the hash gate turns it into a guaranteed WYSIWYG export; then distribution hardening (Developer ID, notarization, TCC onboarding, updater) before any external user touches it. The opportunities the architecture unlocks are non-destructive re-editing (the project is data, render is pure — restyle after recording), golden-frame regression tests with no capture hardware involved, and multi-aspect batch export from one session dir. The risks that compound if deferred are schema versioning, anchors-as-time-series, and the frame-provider contract — all cheap now, all structural later. **Single highest-leverage change: cut phase 1 to the record → cursor-composite → export spine as listed above, and promote the frame-provider contract into increment 0 alongside the schema — it, not the transform, is where preview and export will silently diverge.**

## Issues

Increment 2 alone bundles ScreenCaptureKit display capture, AVFoundation camera/mic, system audio, CGEventTap, segmented writing, and stats into one item. No muxer, audio encoder, track layout, or audio-mixdown decision is specified. At increment 4, the developer will have encoded video/audio chunks and no playable file. This is a mid-build dependency, not a detail.

4. **Lossy stats conflict with the single JSON-lines stdout protocol.** The architecture shows one JSON-lines stdin/stdout channel. The risk table says stats are non-blocking and drop-oldest, while control messages use a separate reliable channel. No separate channel is defined. If stats and control share stdout, a busy Electron process will either back-pressure the helper, violating the non-blocking requirement, or cause partial/dropped lines that corrupt JSON framing.

5. **Segmentation and session files are contradictory.** The architecture names single files (`display.mp4`, `camera.mp4`, `mic.wav`, `sysaudio.wav`, `events.json`), but the long-duration approach says to segment output every N minutes. `render(project, events, t)` has no segment index or mapping. A recording longer than N minutes, or a display change mid-segment, will cross segment boundaries and export will not know which file contains a given `t`.

6. **CGEventTap permission is absent from the signing/TCC section.** Global event tap requires Accessibility/Input Monitoring on current macOS. The doc covers screen capture, camera, and mic, but not the permission that produces `events.json`. In first live capture, the cursor overlay will be missing and the cause will be a TCC grant discovered mid-sprint rather than designed into increment 1.

## Missing

- **Helper protocol spec.** Message versions, request/response IDs, start/stop acks, heartbeats, exit codes, stdout/stderr ownership, stats channel fd, and crash/restart handshake. “JSON-line protocol” is not a spec.
- **Session/segment manifest.** Directory layout, segment naming, sequence numbers, gap handling, manifest fsync policy, and how export maps `t` to a segment. Needed before increment 2.
- **Track availability model.** `render(project, events, t)` must define required vs optional tracks and how missing camera/mic/system audio is represented in `FrameState`. Otherwise “drop the affected track and keep recording” becomes an export-time exception or silently different output.
- **MP4/audio muxing decision.** Pick muxer, audio encoder, track layout, silence handling, and whether phase 1 export is video-only. This should be decided in increment 0 because it affects the render contract.
- **TCC/TCC-preflight declaration.** Exact permissions including Accessibility, how helper startup checks them, and how Electron surfaces denial to the user.
- **Throttling policy.** Stats make drops observable, but the document does not say what happens when encoder fps falls below real-time: drop frames, reduce capture resolution, skip camera, or fail export. Observability alone is not a policy.
- **Input device selection.** The doc says never take the default audio input blind, but no UI or config mechanism exists. If phase 1 has no device picker, the capture start command must accept explicit device IDs.

## Overconfidence

- **Phase 0 “settled” items are overstated on this machine.** Signing is listed as settled while the doc later says the stable-identity experiments still need to be run. `capturesAudio` is described from SDK presence, not from a demonstrated system-audio recording.
- **Timestamp alignment is presented too precisely.** “offset 0 ms, drift 0.0000 ms” and “camera↔mic measured at +1.8 ms median” are point statistics without duration, sample count, or load conditions. A 1.8 ms median offset is not zero and may be visible in lip-sync if not compensated.
- **Child process TCC inheritance is assumed.** “Spawned as child of Electron, which means it inherits Electron’s TCC identity” needs verification with the final bundle and signing arrangement. Process responsibility for TCC is not reliably identical to parent identity for every service.
- **Byte-identical encoded exports may be a false gate.** Two independent WebCodecs/H.264 encodes can be frame-identical after decode but not byte-identical at container/codec level, especially with hardware encoders. The gate should compare decoded frame hashes or raw `FrameState` hashes, not MP4 bytes.
- **Observability is treated as enough for throttling.** A drop to 12.1 fps while recording 60 fps means a growing backlog. The plan needs the response policy before the soak harness, not after it exposes the problem.

## Verdict

Revise it. The pure `render(project, events, t)` core is the right architectural rule and should stay non-negotiable, but the plan is two-to-three solo sprints, not one. Cut phase 1 to display capture + CGEventTap + system audio + transform + CFR MP4 export from a short live session; defer camera, mic, device-loss hardening, and the soak harness to phase 2. Make signing/TCC preflight, including Accessibility, gate zero. Beyond phase 1, the highest-value next phases are: camera/mic with per-device latency compensation, a project/editing model built on the pure transform, and only then real long-duration/thermal/device-change hardening. The pure transform unlocks deterministic headless export, preview/export drift prevention, and later CI or server rendering. The main risk if camera/mic/device-loss are deferred is that the export track model will be designed around display-only and require a breaking schema change later; avoid that by defining optional tracks in the `project` schema now, even if phase 1 does not record them. **Highest-leverage change:** rewrite the increments into exactly four gates: (0) self-signed cert + TCC preflight including Accessibility, (1) freeze protocol/session/muxer schemas, (2) helper + display/system-audio/event capture, (3) Electron shell + one CFR MP4 export; move camera, mic, device-loss, and soak to phase 2.

## Reviewer E

## Issues

**1. Display reconfiguration is treated as a liveness problem; it is actually a timeline-geometry problem, and it lands in the transform.**
"Rebuild the SCStream against the new config rather than dying" is the easy half. The hard half is that a resolution change forces a new video track with different dimensions — H.264 in an `AVAssetWriter` output cannot change dimensions mid-file. So a display change *must* close the current segment and open a new one with new geometry, which means the source timeline is a sequence of segments with **varying width/height/scale/content-rect**, and `render(project, events, t)` must resolve `t` to a frame in a segment whose coordinate space differs from its neighbours. Cursor coordinates from `CGEventTap` are in global display space, which also changed. Nothing in the transform contract, `anchors.json`, or increment 0's fixture accounts for a source whose geometry is a function of `t`. If you build increment 0's fixture as a single fixed-size source, increment 2 invalidates it. This is the most expensive thing in the document and it is one table row.

**2. The increment-0 gate as written cannot pass, for reasons unrelated to your architecture.**
Two problems:
- *"two independent exports of the fixture are byte-identical"* — WebCodecs does not mux. Whatever muxer you use (`mp4-muxer`, `mp4box.js`, hand-rolled) writes `mvhd`/`tkhd` creation and modification times. Those differ between runs. You will spend a day chasing a hash mismatch that is a timestamp field. Even with times zeroed, VideoToolbox rate-control state is not contractually deterministic across process invocations in Chromium (frame-drop-under-load behaviour in `VideoEncoder` is explicitly implementation-defined).
- *"preview frame hash = export frame hash"* — undefined at which surface. If "export frame hash" is the decoded output of the encoded MP4, it can never equal a canvas readback: 4:2:0 chroma subsampling plus lossy encode guarantees mismatch. If it's the pre-encode `VideoFrame`, then the RGBA→YUV conversion path and colour space (`VideoFrame` from canvas is sRGB-tagged; the encoder's `colorSpace` hint) still must be pinned identically on both sinks.

The gate you want: hash the **pre-encode RGBA buffer** produced by the shared renderer, byte-exact, at 200 sampled `t`; and separately assert the muxed file is byte-identical *after* zeroing container timestamps. State both.

**3. "Inherits Electron's TCC identity" is the load-bearing claim and it is the one thing you did not plan to verify.**
Phase 0's whole ethic is "verify rather than assume," and the signing section applies that rigorously to grant-survival-across-rebuild. But TCC attribution for a spawned child is *not* simply inherited — it depends on the responsible-process chain, and ScreenCaptureKit/`CGPreflightScreenCaptureAccess` can attribute to the child's own designated requirement when the child is a separate signed binary rather than a bundled helper at `Contents/MacOS/`. Practically: helper must live inside the app bundle, be signed with the same identity, and you must confirm with `log stream --predicate 'subsystem == "com.apple.TCC"'` that exactly one grant appears and it names the Electron bundle. Add that as an explicit experiment (c) alongside (a) and (b). If it fails, the architecture doesn't change but the onboarding UX does, and you want to know in week 1.

**4. Stats being "non-blocking and lossy" is not achievable over stdout as described.**
Once bytes are in the pipe you cannot drop-oldest. And if Electron's reader stalls (main-thread GC pause, devtools attached, renderer busy), the 64 KB pipe buffer fills and the helper's `write()` blocks — back-pressuring exactly the graph you said must never be back-pressured. Required, and unstated: a ring buffer in the helper, a dedicated writer thread, non-blocking fd with discard-on-`EAGAIN`, and a hard rule that no capture callback thread ever touches the pipe. Also state which fd is which: stdout = lossy stats, stdin + fd 3 (or a unix socket) = reliable request/response with sequence numbers and acks. "Separate reliable channel" is currently a phrase, not a design.

**5. There is no audio in the export path, and audio is not a non-goal.**
`mic.wav` and `sysaudio.wav` are captured in increment 2; increment 4 produces "One CFR MP4 with cursor overlay and camera PiP" — no audio. Mixing mic (device rate, likely 44.1 or 48 kHz) with SCStream audio (48 kHz float) over a 30-minute recording requires a resampler, a drift policy, and a decision about whether the measured +1.8 ms median camera↔mic offset is applied or ignored (you recorded a median, which implies variance you haven't characterised). That is an increment of its own. Either add it or move audio-in-export to phase 2 explicitly — but keep capturing the files.

**6. `displayTimeNs = displayTime × 125/3` is a machine constant stated as a rule.**
41.667 ns is the Apple Silicon `mach_timebase_info`. Intel is 1/1. The table says "here," which acknowledges it, then encodes it as an equation. Rule: read `mach_timebase_info()` at helper startup, apply it, and *write the numerator/denominator into `anchors.json`* so a session recorded on one machine can be interpreted on another.

**7. Segment seams have no defined behaviour, and "hold, never interpolate" makes them invisible failures.**
If segments each restart PTS at 0, you need a per-segment base offset in the global nanosecond timeline, derived from capture time, recorded in `anchors.json`. If the encoder flush at a segment close loses frames, "greatest PTS ≤ `t`" holds the last frame of segment N across the gap — a frozen cursor that looks like a bug in your easing, not a capture gap. Define: seam gap tolerance, whether gaps are recorded as explicit intervals in `anchors.json`, and whether the sink surfaces them.

**8. Increment 1 is marked in progress while increment 0 — the increment that defines the schemas increment 1 emits — is not done.**
The stated order is right. The actual order is inverted. If the helper ships first, `events.json` will be shaped by what ScreenCaptureKit and `CGEventTap` happen to hand you, and the transform will be written against that shape. The rule to state: **the transform defines the schemas; the helper is a producer to spec.** Any field in `events.json` the transform does not read is a field that does not exist.

**9. The thermal finding (18.7 → 12.1 fps) is filed as an observability item, not a product constraint.**
If sustained encode on this machine settles at 12 fps, then VFR-at-capture means a long 4K recording simply contains 12 fps of real frames, and CFR export holds each for five frames. That is a 12 fps video, correctly exported. There is no stated policy for what happens when encoder fps falls below a quality floor: reduce capture resolution mid-session, drop target fps, or warn and continue. Pick one and name the threshold.

**10. Increment 5 has an unpriced hardware dependency.**
"Induced device unplug" cannot be scripted for a built-in camera, and cannot be scripted for a USB camera without a per-port-switchable hub. "Induced display change" needs a second physical display or `displayplacer` against a real one. Either buy the hub and the display, or redefine the soak test as: SIGKILL `VDCAssistant`, and `displayplacer` a resolution/scaling change on the single display. The second is achievable today; say so.

**11. The one part of the product a user can see is absent from the contract.**
"Cursor overlay" is the entire visual surface of this class of tool — smoothing, click emphasis, auto-zoom targeting, cursor scale — and the only representation it has is a table row about frame selection. Specifically: if you exclude the hardware cursor from the SCStream and redraw it (which you must, to smooth and scale it), you need the cursor *image* state over time — I-beam, resize, hidden, custom app cursors. `CGEventTap` gives position and clicks, not appearance. There is no known clean API for observing another app's current cursor image; the practical options are `showsCursor: true` plus never redrawing (kills the craft), or a per-frame `CGSCurrentCursor`-adjacent hack, or accepting a fixed cursor set. This is a genuine unknown, it gates the product's look, and it is not in the risk table.

## Missing

- **The `project` schema.** Increment 0 writes `events.json` and `anchors.json` schemas; `render(project, ...)` takes a third argument with no schema. `project` is the edit document — zoom keyframes, crop, camera layout, easing curves — and it is the thing users will accumulate files of. Decide now: a `version` integer, a `migrate(doc): Project` chain, and `render` throwing on unknown versions. Retrofitting versioning after ten test recordings exist is annoying; after real recordings exist it is data loss.
- **Frame *reference* vs frame *pixels* in `FrameState`.** The purity rule forbids decoder access, which implies the transform returns a reference (segment id + PTS) and the sink resolves it. Say that explicitly, and add the corollary rule: **a sink that cannot resolve a reference blocks or fails loudly; it never substitutes the nearest available frame.** Without that written down, the preview sink will substitute under decode pressure and your equality gate will fail nondeterministically in increment 4, and you will suspect the transform.
- **Recording metadata that cannot be recovered later.** "HDR/P3 non-goal" is fine as a *processing* non-goal and fatal as a *recording* non-goal. Record per-segment: display colour space and transfer function, backing scale factor, `SCStreamConfiguration` content rect, mach timebase, device names and sample rates, cursor scale. Anything you don't write into `anchors.json` in phase 1 is wrong in every session recorded before you fix it. Split the non-goals table into "not processed yet" and "not recorded" — and make the second list empty.
- **Which export frame rates are legal.** The 120 Hz sim implies export fps must divide 120. 60, 30, 24, 20 work; 25 and 50 do not. State the rule and reject the rest at the API boundary.
- **Segment length `N`, and finalisation policy.** Is each segment `finishWriting()`-ed as it closes, so a helper crash loses only the tail? (It should be.) What's `N` — 2 minutes bounds crash loss and keeps seam count low at 30 min.
- **Proxy resolution.** The reference-indirection design gives you proxy editing almost free: preview resolves references against a low-res proxy, export against full-res. Decide now whether `FrameState` references carry a resolution-independent identity, because retrofitting that into the reference type later touches every sink.
- **Self-signed → Developer ID transition invalidates TCC grants.** Expected, but it means your dev-loop grant experience does not predict the shipped one. Note it so you don't debug it twice.

## Overconfidence

- **"Byte-identical" as an achievable gate.** Stated as a settled acceptance criterion. It is an assumption about your muxer and about VideoToolbox determinism, and it will fail first on a container timestamp field.
- **"Inherits Electron's TCC identity — one grant."** Presented as a consequence of process parentage. It is a consequence of bundle layout, signing identity, and responsible-process attribution, none of which are yet true or verified on this machine.
- **"Honest scope note: fully hardening all four is more than one increment."** True and understated. Multi-display hot-swap alone, done correctly, changes the source model that increment 0 bakes in. It is not a hardening task; it is a design input.
- **"Camera/mic are already off the critical path."** True for capture. Not true for export: a mid-recording camera disconnect produces a camera track shorter than the display track, and the transform needs a defined behaviour for "no camera frame at `t`" (hide PiP? freeze last? black?). Currently undefined.
- **Increment 4 estimated as one bullet.** Decode indexing across segments, seek-accurate `greatest PTS ≤ t` resolution, PiP compositing, muxing, and the first real encounter with variable source geometry. This is the largest single item in the list and reads as the same weight as increment 3.
- **Increment 5 as a two-line item.** It has a hardware dependency and no defined pass criteria. "30 min recording with induced X" is a procedure, not a gate. What must be true at the end — zero unrecoverable segments, ≤ *k* dropped frames, monotonic PTS across all seams, export completes?

## Verdict

**Revise — cut hard, don't rethink.** The architecture is right and the settled-decisions table is the most valuable page here: the purity rule, sim-tick determinism, integer-nanosecond timebase, and hold-never-interpolate are the correct four load-bearing constraints, and they're stated as rules rather than described as structures. That part is done. The scope is roughly four to five weeks, not one sprint: increment 0 with a corrected gate is 3–5 days; increments 1–2 are the bulk of the Swift work (four capture sources, segmenting, watchers, non-blocking stats) at 1.5–2 weeks; increment 3 is 2–3 days; increment 4 is a week; increment 5 needs hardware you may not own. And the plan's first milestone as currently ordered is not the one being worked on, which is the tell that scope is set by appetite rather than by the dependency graph.

The sprint-1 cut: **increment 0 and increment 4-against-fixture only — no capture at all.** Hand-authored fixture session, single fixed-size source, one screen video, no camera, no audio, and a fixture that contains real motion (a cursor move with your easing plus a zoom keyframe, sampled at `t` values that deliberately straddle sim ticks and land off the VFR grid). That gets you a real CFR MP4 out of the real transform through the real WebCodecs sink, with the determinism gate green, in one sitting-sized sequence of steps — and it exercises your actual leverage, motion and compositing craft, rather than deferring it behind three weeks of Swift. Sprint 2: helper control plane plus screen capture only, segmented, stats. Sprint 3: camera, audio, device loss, display change. Audio-in-export and multi-resolution timelines are the two things that will force a transform rewrite if you meet them late, so their *data* must be recorded from sprint 2 even though their processing lands in sprint 3+.

Beyond phase 1, the highest-value unlock is nearly free and you should design for it now: because `render` is pure and state is a function of sim tick, you get a **headless CLI exporter** — same transform, third sink — which gives you golden-frame-hash regression tests for the motion design, batch re-export at arbitrary resolution and frame rate, and re-export after edit without re-recording. That last one is the product. Second unlock: proxy preview via resolution-independent frame references. The risks that compound if deferred are all *data*, not code — project schema versioning, per-segment geometry and colour metadata, mach timebase, audio device rates — because every session recorded without them is permanently unrepairable.

**Highest-leverage change: stop work on increment 1. Finish increment 0 first, with (a) a motion-bearing fixture, (b) the gate restated as byte-exact hashes of the pre-encode RGBA buffer plus a timestamp-zeroed container comparison, and (c) a versioned `project` schema alongside `events.json` and `anchors.json` — then write the helper as a producer to those schemas.**

## Reviewer F

## Issues

1. **`AVAssetWriter` will crash on display reconfiguration mid-recording.**
   Rebuilding `SCStream` on `CGDisplayRegisterReconfigurationCallback` delivers frames with new pixel dimensions. `AVAssetWriterInput` cannot change output dimensions mid-stream; passing a resized `CVPixelBuffer` immediately throws an unrecoverable error and corrupts the MP4. Handling display reconfiguration requires finalizing the active `AVAssetWriter`, starting a new segment with new track dimensions, and emitting a segmentation boundary event to `events.json`.

2. **WebCodecs has no native container demuxer, breaking Increment 4 without an unmentioned dependency.**
   WebCodecs accepts `EncodedVideoChunk`, not `.mp4` files. To feed `VideoDecoder` in Electron, you must include a demuxer (e.g., `mp4box.js` or an FFmpeg WASM build). Furthermore, `VideoDecoder` is strictly asynchronous; if `render(project, events, t)` is a synchronous pure function, it cannot directly query the decoder. You need an async pre-fetch/decode cache that sits in front of the render function to deliver the decoded `VideoFrame` matching the greatest PTS $\le t$.

3. **Unfragmented MP4 writes result in total data loss on crashes or power failure.**
   Standard MP4 files write the `moov` atom at file finalization (`AVAssetWriter.finishWriting`). If the helper crashes, runs out of memory, or is killed by the OS, the recorded video files are permanently unreadable. The helper must be configured to output Fragmented MP4 (`AVAssetWriter` with `outputFileTypeProfile = .mpeg4AppleHLS` or movie fragment intervals set) to ensure recorded chunks remain recoverable.

4. **TCC permission inheritance for `CGEventTap` is not guaranteed across process boundaries.**
   Spawning a Swift binary via Node `child_process.spawn` does not cleanly inherit Screen Recording or Accessibility/Input Monitoring permissions unless the helper binary is located in the app bundle's `Contents/MacOS` or `Contents/Helpers` directory, has a designated requirement matching the parent's Team ID, and the parent bundle has the exact entitlement declarations. Loose binaries invoked from development paths fail `CGEventTapCreate` silently (returns `NULL` with no OS prompt).

## Missing

1. **Audio alignment and sample-rate normalization in export.**
   The spec records `mic.wav` and `sysaudio.wav` alongside VFR video, but does not define how the WebCodecs/Web Audio pipeline mixes and resamples them during CFR export. 1. **"MVP scope achievable in a single sprint for a solo developer."**

## Scope Cut (To Fit One Sprint)

To ship a working vertical slice in one sprint, cut the helper to a fixed-configuration recorder and eliminate dynamic runtime mutations:
1. **Cut mid-recording display reconfiguration.** If the display changes, abort recording cleanly and save the file. Do not rebuild the graph mid-stream.
2. **Cut multi-file segmentation.** Record a single continuous take per session.
3. **Cut system audio capture.** Limit Phase 1 audio strictly to the primary microphone input.
4. **Cut Increment 5 (Soak harness).** Validate with manual 5-minute recordings; defer automated fault-injection.

## Beyond Phase 1: Roadmap, Opportunities, and Compounding Risks

### 1. Highest-Value Next Phases
* **Phase 2: Cursor Smoothing & Camera Layout Engine.** Capitalize on your core leverage (interaction and motion craft). Since cursor events are decoupled from render ticks, implement spring-based cursor easing, click ripples, and smart framing/auto-zoom on active inputs.
* **Phase 3: Non-Destructive Clip Trimming & Asset Ingestion.** Add a fast lightweight timeline to mark in/out points and re-order sections without re-encoding the source files.

### 2. Opportunities Unlocked by this Architecture
* **Headless / Cloud Re-Rendering:** Because `render(project, events, t)` is deterministic and decoupled from capture time, the same project file and raw assets can be rendered on a remote server at higher resolutions, alternate aspect ratios (9:16 vertical), or different branding themes with zero re-recording.
* **Post-Hoc Layout Manipulation:** Decoupling camera, screen, and events allows users to reposition the camera bubble, change background padding, or re-generate smooth cursor paths *after* the recording is finished.

### 3. Compounding Risks if Deferred
* **Lack of Fragmented MP4 (fMP4) / Chunked Storage:** If unfragmented MP4 capture is kept beyond Phase 1, any crash in the helper or Electron destroys user recordings irreversibly. Retrofitting fMP4 later requires altering the demuxer, export pipeline, and storage layer.
* **WebCodecs Memory/Queue Architecture:** If the decode-composite-encode loop is built without strict back-pressure mechanisms now, changing it later will require rewriting the core export pipeline.

## Verdict

**Revise it.** The core architectural principle—making `render(project, events, t)` a pure, deterministic function evaluated over discrete simulation ticks—is brilliant and provides massive leverage for post-production craft. However, the helper's scope (display hot-swapping, stream reconfiguration, multi-file segmentation, and live stats channels) is overloaded for an initial vertical slice and contains fatal edge cases regarding `AVAssetWriter` dimension rigidity. Cut the helper runtime down to fixed-stream capture, drop dynamic hot-swapping, and introduce an explicit demuxing/back-pressure layer for WebCodecs.

**Highest-leverage change:** Force `AVAssetWriter` to output Fragmented MP4 (`fMP4`) and strip out mid-recording `SCStream` rebuilding—if the display configuration changes, finalize the recording gracefully rather than attempting to mutate active writer inputs.
